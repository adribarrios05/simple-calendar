# Architecture

## Modules

| Directory | Responsibility |
|---|---|
| `lib/domain` | Pure Dart entities, recurrence, intervals, clock and deterministic scheduler; no Flutter/Drift/SQLite imports |
| `lib/data` | Drift schema, transactional migrations, repository, validated backups and storage failures |
| `lib/application` | Calendar use cases and Riverpod controller; serializes UI operations |
| `lib/presentation` | Navigation, calendars, forms, details, tags and settings |
| `lib/l10n` | Application message resources and Flutter localization delegate; no scheduling or persistence policy |
| `windows` | Native runner and one-instance-per-Windows-session behavior |

CalendarService coordinates repository and pure Planner. Riverpod injects the service; a ChangeNotifier controller holds visible date/view, selection, preferences, definitions, tags and plans. Operations run through a serialized queue and reload visible data. There is no remote infrastructure or synchronization.

Branding uses Simple Calendar in both interface languages, `simple_calendar` as the Dart/CMake project name, and `SimpleCalendar.exe` as the executable. Native version resources use Simple Calendar; storage no longer depends on them. The historical `Local\CalendarioPersonalDesktop` mutex remains stable to prevent simultaneous launches with older binaries in the same Windows session. Legacy database paths and the `calendario-local` JSON format are compatibility contracts, not branding.

The selected logo PNG lives in assets/branding and is bundled as a Flutter asset for navigation. scripts/update_windows_icon.ps1 exports a multi-resolution ICO into the existing IDI_APP_ICON native resource; the executable and native window use that same identity. Source clones and builds do not depend on private logo concept files.

## Domain and persistence

Normal Windows startup resolves `%APPDATA%/Simple Calendar/calendar.sqlite` through `lib/data/data_directory.dart`, independent of native version-resource names. Before Drift opens it, a missing new database can be migrated from the former `local.calendario/calendario/calendario.sqlite` under the same roaming root. The resolver locks a persistent migration lock file, opens the source read-only, checks its supported schema version/integrity, and uses SQLite [`VACUUM INTO`](https://www.sqlite.org/lang_vacuum.html#vacuum_with_an_into_clause) for a consistent snapshot including committed WAL content. It checks the staged snapshot and renames it into place only on success. Failed staging is removed; interrupted staging is never treated as the active database. The source is retained, not deleted or merged. Existing destinations are authoritative and normal database-opening errors apply. The existing schema upgrade to v5 runs on the new copy. Tests inject temporary roaming roots, never the real APPDATA database. Store deployment remains a separate storage-migration gate.

- **Task:** stable UUID, title/description, kind, duration in minutes, fixed start, priority, color, initial date, recurrence, subtasks, optional unique `tagIds`, archived flag, optional inclusive `endDate` and immutable `removedFrom` cutoff. Rules: once, daily, weekdays, weekly or selected weekdays.
- **Tag:** stable local ID, name, opaque color and logical retirement. Eight reserved built-in IDs; names/colors editable, built-ins cannot be retired. Names compare trimmed/lowercase and retired names remain reserved. Membership is stored by ID in snapshots; catalogue names/colors are global and affect historical display.
- **Occurrence:** `(taskId, day)` identity, Task snapshot, pending/completed/skipped state, checked subtask indexes, optional assigned minute, lock and individual exception. Assigning does not change the definition.
- **Preferences:** weekday availability, theme and explicit language (`en`/`es`, default `en`).
- **Span:** `[start, end)` minute interval, allowing consecutive blocks.

SQLite tables: `definitions`, `executions`, `revisions`, `settings`, `tags`. Composite keys prevent duplicate occurrences/revisions; foreign keys prevent orphan rows. Aggregates are validated JSON inside related rows, avoiding separate tables for every checkbox/tag association while keeping snapshots coherent. Application validators enforce payload invariants, including catalogue references; SQL does not constrain every JSON field.

Schema **v5** creation/upgrades are transactional. v1 creates revisions; v1/v2 add tags and seed reserved built-ins. Upgrades from pre-v4 convert archived definitions to permanent removals using their latest archival revision date. v4→v5 changes no table layout or existing payloads: it protects the optional automatic scheduling window contract from older writers. Earlier revisions and execution payloads are preserved. Migration rollback preserves data and user_version. Older binaries reject v5 rather than ignoring new semantics. database.g.dart is generated by build_runner.

Task.autoWindow is an optional same-day Span for automatic tasks only; its JSON representation is a pair of integer minutes, with 0 <= start < end <= 1440. Missing means unrestricted beyond daily availability. Backup v4 carries it in definitions, revisions and execution snapshots; v1/v2/v3 remain importable but cannot claim to contain this new field. Planner intersects free gaps with the task window before rounding starts forward to five-minute multiples and testing the exact full duration. Valid suggestions remain stable. Protected blocks remain untouched and warn outside their window. Explicit assignment also enforces the window. General edits retain protected historical snapshots; single-occurrence edits can deliberately change their window.

Language is an optional field in the existing settings JSON, not a SQL schema change. Missing language becomes English; unsupported values fail validation. Old backups remain readable. Saving theme/availability must carry the current language forward.

## Revisions, history and protection

A general edit creates a revision effective from today. Unmaterialized dates use the latest revision effective on that date, then recurrence is evaluated. This preserves past dates never opened. Multiple edits on one day replace that day's revision; this is not a per-action audit trail.

Only consulted dates are materialized: 1/7/42 in day/week/month. There is no infinite future generation. Completing, skipping and checking subtasks affect only that occurrence.

General edits invalidate pending occurrences from today only when they have no progress, lock, exception or started assignment. The service supplies the full injected clock instant to the repository; revisions remain effective by day. A timed occurrence is started at its initial minute, including a still-pending block whose end has passed. Deliberate changes to it use individual editing.

Tag-only edits update regenerable snapshots in place without removing assignments. Protected snapshots preserve membership. Renaming/recoloring/retiring writes catalogue metadata only. Retirement preserves references/history and removes the tag from new UI selections. Tags never affect Planner policy.

Archival-only saves still preserve existing protected materialized blocks. The explicit **Remove activity** command instead persists an immutable `removedFrom` cutoff in the current definition and its revision. It hides all occurrences on or after that day, including today, without changing their original execution payloads. Day/week/month plans use repository.occurrences, which joins the current definition and filters removed dates. Earlier history stays accessible; allOccurrences/export retains the records for backups. saveTask rejects modification of removed definitions; saveOccurrences rejects writes on removed dates, including stale attempts to unskip or assign them. Repeated removal is idempotent. Existing archived definitions are normalized during database upgrades and v1/v2 backup import. Restore uses a private validated write path so original retained records can be restored without reactivating them.

Task.endDate is an optional inclusive recurrence limit. The editor defaults new tasks to Weekly and offers Every week / This week only for recurring patterns. Week-only uses the start date's Monday–Sunday week, clamped at the supported date maximum; changing that date updates the limit. Existing definitions without endDate remain unbounded. Task.occurs applies the limit for every recurrence pattern without changing planner policy. General edits preserve protected materialized occurrences even when narrowing the limit; creating a new week-only activity never generates later weeks.

Changing editor scope loads saved values for that scope; the current definition never comes from an old snapshot. Unsaved edits are discarded with an explanation. Editing an archived definition through history does not reactivate it.

Subtask progress matches equal text by occurrence order, consuming checked and unchecked duplicates. Adding another equal subtask does not inherit extra checks. Persisted indexes are unchanged.

## Deterministic scheduler

`Planner.plan(day, availability, occurrences)` returns occurrences, per-occurrence issues and free spans. Clock is injectable.

1. Skipped occurrences do not occupy time.
2. Fixed, manual, locked, finished and started assignments reserve their intervals. Incompatibilities preserve positions and report issues on both blocks. Flexible blocks outside availability warn; fixed blocks may exist outside it. Manual placement and conflict previews use the same protection policy.
3. New placements today start after the current instant, excluding a minute already begun. Past days never receive invented automatic assignments.
4. Pending automatic work sorts by descending priority and ascending stable UUID.
5. Valid existing suggestions are reserved first. Future off-grid suggestions round forward to a five-minute boundary if they still fit; otherwise they are displaced. Started/protected/history blocks remain unchanged. New high priority does not evict valid suggestions.
6. New/displaced work uses the first continuous gap fitting the exact duration after rounding its start forward (17:48→17:50). Duration/end are not rounded or extended.
7. Work that does not fit remains unscheduled with an issue. No splitting, deletion or silent protected-block movement.

The scheduler has quadratic work in daily block counts, suitable for the expected personal scale but not a global optimizer. Another arrangement might fit more work.

Manual assignment validates availability and protected blocks; it may displace unprotected suggestions, recalculated on load. Fixed conflict preview inspects weekly recurrence cycles, future starts and materialized exception dates. This seven-day assumption must change with more advanced recurrence. Explicitly accepted conflicts remain visible.

Visible dates recalculate on changes; other dates calculate when opened. A minute timer refreshes the clock and gaps. Month reloads 42 dates and can issue repeated reads/upserts; measure before optimizing. The controller queue currently does not coalesce refreshes.

## Backups and errors

JSON `calendario-local` **v4** contains the full catalogue, definitions, revisions, occurrences and preferences, including optional endDate, removedFrom and autoWindow. v1/v2/v3 imports remain supported; absent fields preserve legacy behavior, and old archived removals are normalized transactionally. v1 restores built-ins with empty memberships. The validator rejects v1/v2 payloads containing the new fields so downgrading a backup label cannot silently lose bounds/removal semantics. IDs, canonical dates, relationships, latest-revision agreement, tags and preferences are validated before replacement. Removed execution data is retained during restore and remains hidden/non-editable. Export remains transactional and uses temporary-file/flush/rename publication.

Recovery tests use temporary databases: late restore failure, revision failure, invalid FK batch, SQLITE_FULL via page limits, SQLite read-only mode and corrupt files. These are bounded simulations, not power-failure/physical-disk guarantees. Storage messages hide SQL and user row values. English domain/storage messages are translated at presentation boundaries. See README for recovery preserving the original.

## Localization and presentation

Fixed-task editing displays start/end clock fields and derives the existing duration in minutes on save. It accepts HH:mm input or Material time pickers, requires an increasing same-day interval, and supports 24:00 only as an end value. Switching to flexible scheduling carries the interval length into estimated duration; switching back derives an end time capped at day end. Scope changes reload both clock fields from the appropriate saved snapshot/definition. No extra persisted end-time field, schema change or scheduler change is needed.

English is explicitly selected by default, independent of Windows language. Settings offers English/Spanish and persists selection. At normal startup, saved preferences are read before constructing CalendarApp, allowing its first frame to use the saved language. A failure before preferences can be read falls back to English diagnostics.

`AppStrings` is a small in-code catalogue with Flutter LocalizationsDelegate, plus Flutter's Material/Cupertino/widget delegates. Templates substitute indexed arguments only after translation. User content is not translated. Known English domain failures are mapped at display boundaries; domain and Planner remain Flutter-independent. No additional dependency or SQL migration is required.

Untouched built-in tag names localize by stable ID/original name; custom/renamed names remain literal. Opening an editor with a localized built-in label and saving it unchanged preserves its stored original name. This avoids rewriting historical snapshots or global catalogue data on language switches.

Domain/navigation share 2000-01-01 through 2100-12-31. Week/month keep 7/42 cells but disable and do not materialize out-of-range dates. Today filters use the injected current day, including midnight transitions. Day heights are one pixel per minute even for short blocks, with tooltip/list alternatives; week has an extra short-block list after unscheduled/skipped items.

## Deliberate limitations

Windows x64, local dates/minutes, same-day continuous blocks, one availability interval per weekday, same-day dragging. DST uses local clock minutes rather than an international timezone calendar. No notifications, background service, vacations, split sessions, deadlines, multi-day scheduler, accounts or cloud. Documentation policy and future language additions are described in CONTRIBUTING.md.
